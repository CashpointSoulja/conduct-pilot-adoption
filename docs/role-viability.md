# Role viability: why I built this for the Deployment Strategist role

Source: the public posting (see `research.md`). This is my reading of it, not inside knowledge.

| The posting asks for | What this concept shows I would do |
|---|---|
| Run the technical deployment hands-on | Scope with baselines and acceptance tests, a dependency walk, blocker ownership, revision-bound evidence |
| Take over post-sale and make it stick | Cohort with denominators, exclusions, unknowns and a role split; a CS handoff that says what is and is not proven |
| Build reusable onboarding and playbooks so capacity compounds | A playbook generated from the gates actually used |
| A direct line into product | A feedback packet that will not let a hunch be filed as verified |
| Comfortable saying "I don't know" | Unknown baselines stay Unknown; small cohorts HOLD instead of reporting a number |
| Builder | A working Worker with SQLite isolation, tests and evals, not slides |

**Honest limits:** I have not worked on SAP projects for this concept, and nothing here tests
real ERP knowledge. The posting says SAP background is not required on day one; the concept is
meant to show how I would run the process around the technology, not that I know the technology.
